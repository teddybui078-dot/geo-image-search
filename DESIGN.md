## Problem Statement

A personal tool that pulls photos from your own macOS Photos library / iCloud (via real permission grant, not upload), extracts GPS location, and plots them on an interactive 3D globe reflecting everywhere you've been. Layered on top: an AI agent you can ask natural-language questions of — "which places did I visit in Europe?", "find me pictures from my trip to Greece" — and it answers by querying your indexed photo metadata and reacting on the globe.

V1 is photos-only (see Premise 4 and the note under Constraints on video). The Greece/Europe example queries are the eventual full vision, including video; for v1 they resolve against photos only.

This is a personal project, not a product. Distribution is not a goal today; open-sourcing it later is likely, so the code should stay reasonably clean, but no packaging is needed yet. **Amended 2026-08-16:** v1 does now ship a minimal first-run onboarding flow (Photos access, agent tone) — the "no onboarding" call above was about a polished, stranger-facing installer flow, not about the app's own first-launch setup, which turned out to matter even for a single user staring at an empty window. The OpenAI API key is deliberately not collected here — `q-and-a-ai-agent`'s `ChatView` already owns key entry with real validation, so onboarding doesn't duplicate it.

## What Makes This Cool

Not a map. Not a search box. A "memory globe" — ask it a question and the globe itself answers spatially: it zooms, highlights routes, surfaces the photos and videos tied to that moment. The 3D-ness and the conversational layer are both explicit choices, not defaults — you specifically want to hand-tweak a colorful, custom-styled globe (not the stock look), and you specifically want the AI layer to be a real agent from day one, not a keyword filter wearing an AI costume.

The person you're building this for first is yourself, reliving trips — but you were honest that as the builder you might not be the one who gets wowed by it. The real "whoa" moment is watching family pull it up and rediscover a trip through your eyes.

## Constraints

- macOS only for v1 (native Photos/iCloud permission access via PhotosKit/Photos framework — not a folder picker, not an upload flow).
- Solo builder, personal use first, family second. No multi-user auth, no billing, no stranger-facing distribution onboarding (a minimal first-run setup flow for the solo user themselves shipped 2026-08-16 — see Premises).
- No firm deadline — the builder explicitly has "plenty of time" and wants to write real code for the ingestion pipeline and the globe rendering, not just wire up existing tools.
- Likely open-sourced eventually, so architecture and code quality matter more than they would for a pure throwaway prototype.
- V1 indexes photos only. Video files are visible in the library scan but their GPS/timestamp metadata is not extracted or indexed in v1 — full video ingestion is deferred (Premise 4). Live Photos are indexed as ordinary photos (image component only; the attached motion/video component is ignored in v1).
- iCloud-only assets (not fully downloaded to the Mac) are a real constraint: requesting full-resolution originals for a large library over the network is slow and storage-heavy. V1 ingestion should request only metadata/location (available without downloading the original) for indexing, and defer full-resolution fetch to on-demand thumbnailing when a photo is actually viewed.
- V1 assumes full Photos library access is granted. macOS also allows granting only a "Selected Photos" subset — if the user picks limited access, v1 indexes whatever subset it's given; the onboarding flow now explains what's being requested and why before prompting (TODOS.md item 6), but does not yet warn separately if the user chooses the limited option specifically.
- Designed for a personal library on the order of tens of thousands of photos (~50k), not a shared or professional-scale archive — this bounds the feasibility of per-photo reverse geocoding and embedding generation below.
- Family use means someone else operating the builder's own Mac/session, not a separate account or login — consistent with "no multi-user auth" above.

## Premises

1. Personal/family tool — no multi-tenant auth, no billing, no stranger-facing distribution needed.
2. V1 = real macOS Photos/iCloud permission grant → EXIF/GPS extraction → interactive 3D globe with pins → AI chat agent answering natural-language questions, all from day one (not deferred to a later phase).
3. Photo ingestion (EXIF parsing, permission flow, thumbnailing) is being built from scratch, not delegated to an existing tool like Immich — a deliberate choice, made knowing it duplicates solved open-source work, because building it is part of the fun and the learning.
4. Video support, auto-generated trip stories/recaps, and shared/social family maps are explicitly deferred past v1 — they're the confirmed 10x roadmap, not now.
5. No distribution/packaging needed now; code should stay reasonably clean since open-sourcing later is likely, but no installers needed yet. (Amended 2026-08-16: a minimal first-run onboarding flow — Photos access, API key, agent tone — was added; "no onboarding" here always meant no installer/distribution-grade onboarding, not the app's own first-launch setup.)
6. The AI agent is a real tool-calling agent from day one, not a narrow keyword/date parser standing in for one — confirmed explicitly after independent pushback on this exact point (see Cross-Model Perspective below).
7. Photos with no GPS data (screenshots, location-services-off shots, older imports) are still indexed for date and semantic search, but are excluded from globe pins — there's nowhere to plot them.
8. `cluster_trips` (grouping pins by time+proximity to answer a query, e.g. "my Greece trip") is v1 scope. Turning those clusters into a written narrative/recap (Premise 4's "auto-generated trip stories") is not — `cluster_trips` returns structured groups for the agent to answer with, it does not generate prose.

## Approaches Considered

### Approach A: Weekend Prototype
Web app (Vite+React), folder picker instead of native Photos permission, CesiumJS globe, exifr for EXIF, SQLite for metadata, OpenAI function-calling agent with 3-4 simple tools (search by place/date/keyword).
- Pros: ships the full ask-a-question-globe-reacts loop fastest; minimal infra, one SQLite file.
- Cons: folder picker isn't the real native Photos/iCloud permission flow the builder wants; naive text search gets sluggish past a few thousand photos without embeddings.
- Rejected: does not satisfy the explicit requirement for real native permission-based photo access.

### Approach B: Native Permission + Full Agent (chosen)
Real macOS app (Tauri shell or native Swift host) requesting actual Photos/iCloud library access via PhotosKit/Photos framework. GPS comes directly from `PHAsset.location` — no manual EXIF byte-parsing needed for coordinates; raw EXIF parsing is only pulled in later if a specific field PhotosKit doesn't expose turns out to matter. Reverse geocoding (lat/lon → city/country/continent, needed to answer "places in Europe"-style queries) runs during ingestion via `CLGeocoder`/MapKit, bucketed by lat/lon rounded to ~1km (refine if the correctness test set shows nearby-town misattribution) so photos taken near each other share one cached lookup, with requests throttled — CLGeocoder is rate-limited and not built for naive per-photo bulk calls. `semantic_search` requires a joint text/image embedding space (a free-text query and a photo embedding must land in the same vector space to be compared) — Apple's built-in Vision scene/object classifiers produce a fixed label taxonomy, not that, so v1 bundles a CLIP-style on-device model (CoreML-converted, e.g. MobileCLIP) for both photo and query embedding, stored via SQLite + sqlite-vec alongside structured metadata. Embedding generation reads PhotosKit's local low-resolution thumbnail (typically already cache-served, not a full-resolution iCloud fetch) — but it still touches every asset's image bytes once, which is a real per-library cost worth expecting up front, distinct from the full-resolution fetch that stays deferred to on-demand viewing. A real LLM tool-calling agent (tools: query_by_location, query_by_date_range, semantic_search, cluster_trips), using the OpenAI API, sits on top, talking to a custom-styled 3D globe built on top of OpenGlobus in an embedded webview.
- Pros: matches the actual permission model the builder wants; scales cleanly into video, trip clustering, recaps, and sharing later without a rewrite; leaves room for the globe's visual identity to be hand-tweaked.
- Cons: native Photos/iCloud integration has real permission-prompt friction and sandboxing rules to work through; most moving parts of the three approaches, slowest to a first working loop.

### Approach C: Local-First Privacy-Native
Local-first web app watching an iCloud/Drive-synced folder, local embeddings (CLIP via transformers.js), local LLM agent (Ollama), deck.gl GlobeView or react-globe.gl for the globe.
- Pros: zero cloud dependency, fits the "open source later" goal well — anyone can clone and run it with no API keys.
- Cons: "grant photo access" becomes "point me at a synced folder," a step removed from the real permission-prompt UX the builder specifically wants; local LLMs are meaningfully weaker at agentic tool-calling than GPT/Claude-class models.
- Rejected: same reason as A — sidesteps the native permission model that's a hard requirement, not a nice-to-have.

## Recommended Approach

**Approach B**, confirmed by the builder after explicitly rejecting the folder-upload alternative twice. The native Photos/iCloud permission integration is treated as a hard requirement, not a convenience — this is the piece of the product that makes the permission model real rather than simulated. The globe itself (OpenGlobus as the rendering base, custom-styled/colorful, hand-tweaked rather than used stock) and the agent (real tool-calling from day one, not a keyword parser) are both explicit, informed choices to keep the harder, more interesting engineering in scope rather than deferring it.

- How thumbnailing and vector embedding generation are triggered — **Resolved (/plan-eng-review):** background queue, bounded concurrency, visible progress, with an optional date-range scope for first-run indexing (e.g. "2021-present first") to reduce cold-start cost.
- ~~How the app detects new/deleted assets in the library on relaunch (one-shot full ingest vs. incremental diff sync)~~ **Resolved (`photo-icloud-extraction` branch):** full library enumeration every launch (cheap, metadata-only, no image bytes), diffed client-side against `PhotoQuery.allActiveIdentifiers()` using `PHAsset.modificationDate` as the change signal — not Apple's `PHPersistentChangeToken` API. First launch falls out of the same code path for free (empty stored set = everything's new), no separate one-shot-ingest branch. Full reasoning: CONTRACT.md's "Relaunch sync strategy" section.
- Whether overlapping pins from burst/duplicate shots at the same place and time need explicit visual clustering — deferred until real library data shows how noisy this actually is; not a v1 blocker. (Distinct from the LOD/clustering added below, which is about raw rendering performance at scale, not duplicate-photo visual noise.)

## Architecture Decisions (/plan-eng-review, 2026-08-09)

- **Native↔globe IPC:** WKWebView message handlers (`WKScriptMessageHandler`) for native Swift → JS, `window.webkit.messageHandlers` for JS → native. Keeps SQLite/PhotosKit fully native while the globe stays pure JS; needs a versioned message schema as the tool surface grows.
- **LLM API key storage:** macOS Keychain (Security framework), not a config file or environment variable. Agent tool outputs are treated as structured data the LLM reads, not instructions it executes — low injection risk for a single-user personal tool.
- **Shared query layer:** A `PhotoQuery` repository/builder used by all four agent tools (`byLocation`, `byDateRange`, `bySimilarity`, `clusterTrips`) instead of four independent SQL builders — avoids duplicating the same base filters (GPS-present, date bounds) four times.
- **Error handling:** One shared error-reporting/logging surface across PhotosKit, CLGeocoder, and LLM calls (consistent UI presentation), but each boundary gets its **own retry policy** (backoff timing, retry count, what counts as retryable) rather than one-size-fits-all retry logic — refined from an initial fully-unified design after outside-voice review flagged that PhotosKit/geocoding/LLM/iCloud/CoreML failures have genuinely different retry semantics.
- **Geocoding provider:** Keep CLGeocoder (not an offline dataset) — the existing ~1km bucketing + caching + throttling design already collapses most of the call volume a personal library generates. Revisit only if real ingestion runs actually hit throttling.
- **Geospatial index:** SQLite's built-in R-Tree virtual table module for lat/lon/radius queries (`query_by_location`). sqlite-vec handles embedding similarity only — it does not solve geospatial range queries, which R-Tree is purpose-built for and ships with SQLite already (no new dependency).
- **Asset identity model:** `PHAsset.localIdentifier` as the stable SQLite primary key, with a `deleted_at`/`updated_at` pattern so relaunch sync (Next Steps 1a) can diff against it — decided now to avoid rebuilding embeddings/geocode rows later if the ingest model changes after the library is already large.
- **Globe rendering at scale:** Level-of-detail/clustering planned in from the start (zoomed out = country/city clusters, zoomed in = individual pins). **Correction, from `add-3dmap`:** OpenGlobus turned out to have no built-in Entity/Layer clustering (checked directly against its source and compiled bundle — no trace of it anywhere), contrary to what this line originally assumed. Implemented instead as a hand-rolled lat/lon grid in `Globe/Resources/globe.js`, sized by camera altitude and recomputed on zoom — necessarily client-side JS, since native has no visibility into live camera state to drive it.
- **3D globe vs. native 2D map, reaffirmed:** The interactive 3D globe (not a native MapKit 2D view) stays as Next Step 3, after outside-voice review proposed a faster-validating 2D-first sequencing. Reaffirmed because the 3D globe is the project's core differentiator and the reason it feels like "yours," not a detour — this was already explicitly chosen over 2D alternatives (Approaches A and C) during office-hours, and reconfirmed here.
- **Real tool-calling agent, reaffirmed (3rd confirmation):** Stays as a real agent from day one rather than a deterministic query planner, after outside-voice review raised this critique again. Consistent with two prior explicit confirmations during office-hours.
- **Webview failure fallback:** `WKNavigationDelegate` detects load failure/crash and swaps in a native SwiftUI error view ("Globe failed to load — retry") instead of leaving a silently blank window — the WKWebView bridge was otherwise the one codepath in the test coverage diagram with no planned test *and* no planned error handling for a user-visible failure.

## Success Criteria

- Grant macOS Photos/iCloud permission through the app and see your own real photos, with GPS data, plotted as pins on a working 3D globe. Photos without GPS data are indexed but don't appear on the globe.
- Ask the agent a real question ("where did I go in Europe?", "find pictures from Greece") and get a correct answer that also updates the globe view. "Correct" means: 100% of a small, fixed, hand-written test set of representative questions with known-expected answers/pin sets passes, manually run each time the tool surface changes (Next Steps 5-6) — not scripted CI in v1.
- The globe's visual style is something you built/tweaked yourself, not OpenGlobus's default look — concretely: no default blue-marble basemap, custom pin/cluster glyphs, and your own color palette.
- A family member (using your own Mac/session) can open it and find a specific trip without you explaining how it works.
